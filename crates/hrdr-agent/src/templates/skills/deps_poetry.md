---
name: deps_poetry
description: update Python dependencies (poetry) to latest stable
---

Update a Python project's dependencies under poetry (`pyproject.toml` +
`poetry.lock`).

- **Detect**: `pyproject.toml` with a `[tool.poetry]` section + `poetry.lock`.
  If the project uses uv instead (`uv.lock`), use `:deps_uv`.

- **Current lockfile**: `poetry update` re-resolves the lock against the
  current constraints and installs; `poetry update <pkg>` one package.
  `poetry lock` regenerates the lock WITHOUT upgrading anything beyond the
  constraints (use `poetry lock --no-update` to re-lock exactly what's already
  there). `poetry show --outdated` lists what's behind.

- **Latest stable**: `poetry add <pkg>@latest` raises one dependency's range
  and locks it (the `@latest` syntax resolves the newest stable). For an
  existing dependency, `poetry add <pkg>@latest` updates the range;
  `poetry update <pkg>` keeps the range but takes the newest that satisfies it.

- **Lockfile**: `poetry.lock` is regenerated by `poetry update`/`poetry add`;
  commit it with the manifest. CI gates run `poetry install --sync` (or
  `--no-root`/`--only main` as the project does); a stale lock fails
  `poetry check --lock` — run that before committing.

- **Verify**: `poetry install`, then the project's test/lint/build commands
  (via `poetry run`). Check the installed copy under the virtualenv
  (`poetry run python -c "import <pkg>; print(<pkg>.__file__)"`) for changed
  APIs.

- **Gotchas**: `requires-python` caps what resolves — raise it deliberately
  before expecting the newest releases. Poetry keeps its own hash of the
  lockfile in `pyproject.toml` (a `content-hash` inside `poetry.lock`); any
  manifest edit without a re-lock fails `poetry check --lock`, which is the
  same gate CI uses.
