---
name: deps_bundler
description: update Ruby dependencies (bundler) to latest stable
---

Update a Ruby project's dependencies under bundler (`Gemfile` + `Gemfile.lock`).

- **Detect**: `Gemfile` + `Gemfile.lock` (a `*.gemspec` for a gem's own
  dependencies — the gemspec pins flow through the Gemfile in a standard gem
  layout). If the project uses a lockfile from another manager, use that
  manager's run book.

- **Current lockfile**: `bundle update` re-resolves the lock against the
  current constraints; `bundle update <gem>` one gem (repeatable:
  `bundle update <gem1> <gem2>`). `bundle outdated` lists what's behind.

- **Latest stable**: `bundle update <gem>` keeps the `Gemfile` range; to cross
  a major, edit the `Gemfile` constraint and `bundle update <gem>`. For
  everything to latest: `bundle update` (all, within ranges) — bulk
  major-crossing is per-gem in the Gemfile, or via Dependabot/Renovate in CI.

- **Lockfile**: `Gemfile.lock` is regenerated by `bundle update`; `bundle lock`
  re-locks without changing versions. Commit the lock with the manifest;
  `bundle install` respects the lock, and CI with a frozen gate runs
  `bundle install --frozen` (or `bundle check` + `--deployment` in the classic
  flow), which fails if the lock drifted from the Gemfile.

- **Verify**: `bundle install`, then the project's test/lint commands
  (`bundle exec rspec` / `bundle exec rake` as defined). Check changed APIs in
  the installed gems (`bundle show <gem>` → path, then read the unpacked
  source).

- **Gotchas**: Ruby version requirements (`ruby "~> X"` in the Gemfile and
  `required_ruby_version` in gemspecs) cap what resolves — raising them is
  part of the update and sets the runtime floor. Platform-specific gems
  (native extensions) may lag a bump until prebuilt binaries catch up — if an
  install fails on your platform, the gem's release may simply not have a
  binary yet; say so rather than forcing a source build. Never hand-edit
  `Gemfile.lock` — bundler treats it as authoritative and re-derives it.
