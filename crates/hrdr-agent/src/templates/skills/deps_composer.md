---
name: deps_composer
description: update PHP dependencies (composer) to latest stable
---

Update a PHP project's dependencies under composer (`composer.json` +
`composer.lock`).

- **Detect**: `composer.json` + `composer.lock` at the project root (plus
  `composer.lock` per package in a monorepo with `composer.json` in
  subdirectories).

- **Current lockfile**: `composer update` re-resolves the lock against the
  current constraints; `composer update <pkg>` one package, `composer update
  <pkg1> <pkg2>` several. `composer outdated` lists what's behind with
  `--direct`/`--major-only` filters. `composer validate` checks the manifest.

- **Latest stable**: `composer require <pkg>:^X.Y` raises a dependency's range
  (caret to the new major). For "everything to latest": `composer update` keeps
  ranges — crossing majors needs the ranges raised per package, or a bulk
  tool (e.g. `composer-outdated`-driven or Dependabot/Renovate in CI).

- **Lockfile**: `composer.lock` is regenerated by `composer update` /
  `composer require`. `composer update --lock` re-locks WITHOUT upgrading
  versions (equivalent to a re-resolve of the current pins). Commit the lock
  with the manifest; CI runs `composer install --no-interaction` which uses
  the lock, and `composer validate --strict` catches a manifest/lock drift.

- **Verify**: `composer install`, then the project's test/lint commands
  (`composer test` / `composer run-script` as defined). Check changed APIs in
  `vendor/<pkg>/` (the installed copy).

- **Gotchas**: platform requirements (`"php": ">=8.x"`, ext-* extensions) cap
  what resolves — raising them is part of the update and affects the runtime
  floor. `composer install` respects the lock; if CI appears to "ignore" your
  bump, the lock didn't get committed. Never hand-edit `composer.lock` — it is
  content-hashed against `composer.json`.
